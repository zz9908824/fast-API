# 政务材料预审系统：P0 前端、数据库与 API 对接说明

本项目采用“前端 → FastAPI → PostgreSQL”的单向访问方式。浏览器不直接连接数据库，也不获得数据库账户或文件存储键。

## 已实现的数据库边界

迁移按顺序执行：

1. `20261010_gov_precheck_core_schema.py`：事项、事项版本、材料要求、办件、参与人、文件版本、核验与复核等核心表。
2. `20261010_precheck_api_support.py`：为前端交互增加问卷状态、配置/任务修订号、准备声明、复核消息和幂等请求记录。

前端每次修改办件都提交 `expected_revision`。后端仅在该值等于 `applications.content_revision` 时写入；不相等返回 `409`，前端应重新读取办件后提示用户处理冲突。

## 已可调用的接口

所有路径均在 `/api/v1` 下；接口响应使用 `{ "data": ... }` 包装。

| 前端功能 | 方法和路径 | 登录要求 | 数据表 |
| --- | --- | --- | --- |
| 公开事项列表 | `GET /matters` | 否 | `service_matters`、`matter_versions` |
| 事项详情与材料清单 | `GET /matters/{matter_id}` | 否 | `material_requirements`、`material_types` |
| 获取材料渠道 | `GET /matter-versions/{version_id}/requirements/{requirement_id}/acquisition-methods` | 否 | `material_acquisition_methods` |
| 查看已核验来源 | `GET /policy-sources/{source_id}` | 否 | `policy_sources` |
| 新建办件 | `POST /applications` | 是 | `applications`、`api_idempotency_records` |
| 我的办件、办件详情 | `GET /applications`、`GET /applications/{id}` | 是 | `applications` 等 |
| 保存/提交问卷 | `GET /applications/{id}/questionnaire`、`PUT /applications/{id}/scenario` | 是 | `applications.scenario_answers` |
| 参与人 | `GET/POST /applications/{id}/participants` | 是 | `application_participants` |
| 个性化清单 | `GET /applications/{id}/checklist` | 是 | `material_requirements`、`application_preparation_items` |
| 标记线下材料准备情况 | `PUT /applications/{id}/preparation-items` | 是 | `application_preparation_items` |

`POST /applications` 必须传 HTTP 请求头 `Idempotency-Key`。同一用户以相同键重试相同请求，返回首次创建的办件；同键而请求内容不同，返回 `409`。

## 前端接入方式

现有页面中的演示数据仅用于原型展示。正式接入时，以 OpenAPI 重新生成 `frontend/src/client`，然后用生成的客户端调用上表接口；不要手写数据库连接。

```ts
// 例如：GET /api/v1/matters?q=...
// 返回 { data: MatterSummary[] }，页面状态由 data 驱动。
```

事项配置需要先由管理员写入并发布一个 `matter_versions.status = 'published'` 的版本，公开事项接口才会返回它。项目不会自动写入真实政务事项或政策来源，避免把演示数据误当成官方数据。

## 尚未实现的受控能力

文档中的文件上传、OCR/模型解析、异步核验、人工复核工作台、管理端配置 CRUD 仍需要文件存储、后台任务执行器、角色授权与审计策略。它们已有数据库表和 API 契约，但尚未开放端点，因此前端不能显示为“已经完成预审”。
